# ADR-025: `mesh mcp install` is one table per client

2026-10-05, goal `mesh-mcp-installs-into-claude-codex-and-cursor`
(item 2, amended by item 3's render). Numbered 025 beside
`adr-025-a-node-says-which-sessions-it-takes.md` and
`adr-025-items-that-share-a-file-are-planned-in-a-line.md`; cite this
one as "ADR-025, mesh mcp install". Amends ADR-023's Skill section,
which wrote Claude Code's skill alone and printed `claude mcp add`.

## Context

`mesh mcp` is a stdio MCP server any client can run, but `mesh mcp
install` knew only Claude Code: a Codex or Cursor user had to write the
server entry by hand and had no `/mesh` instructions at all. Each
client keeps its servers in its own file and format, and those files
are the person's — other servers, settings, comments — so an install
that round-trips them through a map loses what it does not understand.

## Decision

1. **One table.** `internal/mcpinstall/clients.go`'s `Clients()` returns
   one `Client` row per client in a fixed order — claude, codex,
   cursor: `ConfigDir(home)` (honouring the client's own environment
   variable where its documentation names one), the MCP file
   (`MCPConfig` relative to it, or `MCPFile` when the file sits outside
   it, as Claude's `.claude.json` does), its `Format` (JSON or TOML),
   the entry's JSON path `MCPKeys` or `TOMLTable`, its `Instructions`
   (`InstructionFile{Path, Kind whole|marked-section, Marker, Body}`),
   and the `Binaries` `Detect` looks for on PATH beside the config
   dir. A fourth client is one more row.
2. **One source.** Every entry is `Entry(exe, remote)`: the absolute
   path of the running mesh binary with `args ["mcp"]` — JSON
   `{"type": "stdio", "command": …, "args": ["mcp"]}` (`type` because
   both Claude Code's and Cursor's documented stdio examples carry it),
   TOML `command = "…"` / `args = ["mcp"]` quoted as the Codex harness
   quotes (`TOMLString`). Every instruction file renders from
   `meshmcp.Skill()`; a row whose `Body` is nil is recorded here and
   written by item 3 of the goal. `--remote` (item 4) writes
   `RemoteEntry` instead: see Remote below.
3. **Never clobber.** `Plan(home, exe, clients, opts)` reads each file
   and upserts with item 1's `UpsertJSONFile`/`UpsertTOMLTableFile`:
   an existing `mesh` entry's span replaced in place, every other byte
   kept. A file its parser cannot read is an `*UnparseableError`,
   printed `<path>: cannot parse (<err>); left alone`; a whole
   instruction file that differs from what mesh-cli ships is a
   `*DiffersError` unless `--force`. Either leaves that file out; the
   other files and clients are still written and the command exits 1.
   `Apply` writes only changed files (`node.WriteFile`, 0644 for a new
   file, directories made), so a re-run touches nothing and reports
   every file `unchanged`; otherwise `wrote` (absent before) or
   `updated`.
4. **Dry run.** `--dry-run` prints `Diff` for every change — the same
   `---`/`+++` header and `+` lines the real run would apply — then
   `would write <path>`, and writes nothing.
5. **Which clients.** `--client` is repeatable or a comma list of
   claude, codex, cursor or all; left out, every client `Detect` finds
   (config dir present, or a binary on PATH), and none found is `no
   client found; pass --client`. The `claude mcp add` line is printed
   only when the Claude row was chosen and its entry could not be
   written.
6. **One render, per client (item 3).** `internal/mcpinstall/instructions.go`'s
   `Render(client, skill) ([]Rendered{Path, Body, Marked}, error)`
   parses the skill once — its frontmatter (`name`, `description`) and
   body — and renders every client's instruction files from it, so
   they never drift: Claude's is the skill whole, unchanged; Codex's
   prompt is the body with a leading `<!-- generated by \`mesh mcp
   install\`; … -->` comment, every `` `/mesh <form>` `` mention — a
   form heading's full line or a bare inline one, found by one regex
   over the whole body, not headings alone — turned into
   `` `/prompts:mesh <form> $ARGUMENTS` `` (or with no argument hint on
   that form's own heading, `` `/prompts:mesh <form>` ``) — Codex's
   prompts take one `$ARGUMENTS` blob, per its documentation — and its
   AGENTS.md section is the same body, `Marked`; Cursor's user skill is
   the same frontmatter and body with its own client-specific lines,
   its command the body alone, and its rule the body with
   `alwaysApply: true` frontmatter in place of the skill's `name`/
   `description` — all three keeping the skill's own `/mesh <form>`
   naming, since Cursor's forms are not renamed. The body's
   client-specific lines — `claude mcp add mesh -- mesh mcp`, "from
   Claude Code" — are rendered through a small substitution table per
   client (`codexSubstitutions`, `cursorSubstitutions`), never a second
   copy of the text. `UpsertMarked(src, body, begin, end)` (new in
   edit.go, beside `UpsertMarkedFile` and `Markers(marker)`) replaces
   the span between `begin` and `end` in place, appends the section
   after one blank line when the markers are absent, and keeps every
   byte outside; `planInstruction` calls it for a `MarkedSection` row
   instead of the whole-file `--force` rule, so a marked section is
   always upserted, never refused for differing.
7. **Cursor gets no rule file (item 3's amendment, review 2026-10-12).**
   Cursor's "User Rules" are a Customize → Rules setting in the app,
   not a file on disk (docs.cursor.com/docs, fetched 2026-10-05); its
   one file-based rule mechanism is a **project** rule,
   `.cursor/rules/*.mdc`. `mesh mcp install` is a per-user install, so
   it never writes into the directory it runs from — a rule dropped
   into whatever repository the person stands in could be committed
   there by accident. The user skill and command carry the
   instructions; a project rule, if ever wanted, is its own explicit
   flag.

What the documentation said that shapes the rows:

- **Claude Code**: user-scope servers are stored in `~/.claude.json`
  under `mcpServers`, and the configuration directory moves with
  `CLAUDE_CONFIG_DIR`; personal skills are
  `~/.claude/skills/<name>/SKILL.md`. Writing the entry directly is
  what `claude mcp add --scope user` does, so the old hint is no
  longer needed.
- **Codex**: `[mcp_servers.<name>]` with `command`/`args`/`env`, or
  `url` with `bearer_token_env_var`/`http_headers` (the shape item 4's
  `--remote` writes); `CODEX_HOME` moves the global `AGENTS.md` (an
  `AGENTS.override.md` there wins). Custom prompts live in
  `~/.codex/prompts/` and are documented as **deprecated** in favour of
  skills, which Codex reads from `~/.agents/skills` — outside
  `CODEX_HOME`; the prompt row stands as the goal asked, and moving it
  to a skill is one row change.
- **Cursor**: `~/.cursor/mcp.json` under `mcpServers`, stdio
  `type`/`command`/`args`/`env` or remote `url`/`headers` with
  `${env:NAME}` interpolation; no environment variable moves it.
  **User rules are not files** — "User Rules are global preferences
  defined in Customize → Rules … that apply across all projects," per
  docs.cursor.com/docs (fetched 2026-10-05) — so a user skill at
  `~/.cursor/skills/<name>/SKILL.md` (`name` and `description`
  frontmatter), which the docs name as the global path, carries the
  instructions every client gets. Cursor's one file-based rule is a
  **project** rule, `.cursor/rules/*.mdc` (`description`, `alwaysApply`,
  `globs` frontmatter), "version-controlled with your codebase" and
  read only from the project Cursor has open — so the install writes
  none (decision 7): it is per-user, and the user skill and command
  carry the instructions. Custom
  commands are being migrated to skills (`/migrate-to-skills`) and the
  docs no longer name `~/.cursor/commands`, which the row keeps for
  Cursor versions before it.

## Remote

2026-10-05, item 4. `mesh mcp install --remote` is the no-binary path:
each chosen client gets an entry for the hosted MCP server instead of
`<exe> mcp`, and the instruction files are written as for a local
install.

1. **The URL** is `--url`, else the gateway's `/mcp` beside the
   configured gateway (`--gateway`, `$MESH_GATEWAY`, node.yaml's
   `gateway`, else `https://api.runsheet.dev`), built by
   `node.MeshMCPURL` — the same URL mesh-context sessions get.
2. **Discovery, once.** `mcpinstall.DiscoverAuth(ctx, url)` reads the
   server's protected-resource metadata (RFC 9728:
   `/.well-known/oauth-protected-resource` inserted before the URL's
   path, then at the host's root), and for each of its
   `authorization_servers` the issuer's metadata (RFC 8414
   `oauth-authorization-server`, then `openid-configuration`, path
   inserted then appended). A `registration_endpoint` (RFC 7591) is
   `OAuth{Issuer}`; anything else — no metadata, no issuer, no
   registration, a network error, ten seconds passing — is
   `Bearer{EnvVar: "MESH_TOKEN"}` (`BearerEnvVar`, the variable the
   mesh CLI itself prefers over `~/.mesh/token`). The command prints
   `url: <url>` and `auth: oauth (dynamic registration at <issuer>)` or
   `auth: bearer from $MESH_TOKEN`. Dynamic registration is Latchkey's
   goal `an-mcp-client-signs-in-with-one-click` (its ADR 006, proposed
   on 2026-10-05, not landed): until its issuers serve
   `registration_endpoint`, discovery answers bearer.
3. **Never a token in a file** (ADR-006: secrets in the environment
   only, the config holds the name). A bearer entry names
   `MESH_TOKEN` in the client's own reference form; the person exports
   it (e.g. an `rs_*` console token) where the client runs. An OAuth
   entry is the URL alone: Claude Code and Cursor discover the issuer
   from the URL themselves, and Codex's `auth` defaults to `oauth`, so
   the install prints a `codex: sign in with … codex mcp login mesh` line.
4. **The rows' remote shapes** (`RemoteEntry(client, url, auth)`; a
   JSON row's `RemoteType` and `EnvRef`, a TOML row's
   `bearer_token_env_var`). An existing `mesh` entry — stdio or
   remote — is replaced in place by the same upsert, so moving between
   the two is one re-run.

| Client | Bearer entry | OAuth entry | Documentation (fetched) |
|---|---|---|---|
| claude | `mcpServers.mesh` = `{"type":"http","url":"<url>","headers":{"Authorization":"Bearer ${MESH_TOKEN}"}}` — `${VAR}` expanded in `url` and `headers`; credential variables such as `ANTHROPIC_API_KEY` read as empty there, `MESH_TOKEN` is not one | `{"type":"http","url":"<url>"}` — OAuth discovered from RFC 9728/8414 metadata | https://code.claude.com/docs/en/mcp (2026-10-05) |
| codex | `[mcp_servers.mesh]` `url = "<url>"`, `bearer_token_env_var = "MESH_TOKEN"` | `url = "<url>"` alone (`auth` defaults to `oauth`; `codex mcp login mesh`) | https://learn.chatgpt.com/docs/extend/mcp?surface=cli (2026-10-05) |
| cursor | `mcpServers.mesh` = `{"url":"<url>","headers":{"Authorization":"Bearer ${env:MESH_TOKEN}"}}` — remote entries carry no `type` in the docs; `${env:NAME}` interpolation | `{"url":"<url>"}` — `auth` (`CLIENT_ID`/`CLIENT_SECRET`) only for a static client, scopes discovered from `/.well-known/oauth-authorization-server` | https://cursor.com/docs/context/mcp (2026-10-05) |

## Consequences

- A client's file format or path changing is one row and one date
  here, not new code.
- Writing `~/.claude.json` directly races Claude Code rewriting it;
  the upsert is a read-modify-write of one span, and a person running
  install while Claude Code is open may need to run it again.
- Every row now has a `Body`, Codex's and Cursor's rendered through
  item 3's `Render`; `mesh mcp doctor` (item 5) reads the same table.
- A marked section is never refused for differing (unlike a whole
  file): re-running always lands the current skill's text inside the
  markers, even after a person edited it there by hand.
